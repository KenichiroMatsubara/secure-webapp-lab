# 安全設計（SAFETY）

このラボは**わざと脆弱なアプリ**です。インターネット上に置く以上、「想定外の人が攻撃に使う」「自分のアカウントや評判に傷がつく」リスクを先に潰しておく必要があります。何をどう防いでいるかを、脅威ごとに整理します。

## 想定する脅威

| # | 脅威 | 例 |
|---|---|---|
| T1 | 第三者がアプリに到達する | 検索で見つかる、URLが漏れる |
| T2 | 他の学習者のデータが見える・壊れる | SQLインジェクションで全データを読む |
| T3 | アプリが攻撃の踏み台になる | オープンリダイレクトでフィッシング、XSSで外部へ送信 |
| T4 | アプリが外部へ攻撃・通信する | SSRF、OSコマンドで外部へ接続 |
| T5 | 実環境が侵害される | OSコマンド・ファイル読み取りでサーバーを操作される |
| T6 | データが残り続ける | 古い学習データがいつまでも残る |
| T7 | 設定ミスで保護が外れる | Access のポリシーを誤って外す |

## 対策

### T1・T7: 入口を閉じる（多層）

1. **Cloudflare Access** で、許可したメールアドレスの人だけを通します。
2. **アプリ自身が Access の JWT を検証**します（`src/lab/access.ts`）。署名（RS256）、`iss`、`aud`、有効期限を確認し、`alg=none` や別の鍵での署名は拒否します。`ENVIRONMENT` が `development` 以外では常に検証し、**設定が空なら全リクエストを 503 で拒否**します（fail-closed）。`ALLOWED_EMAILS` で許可メールも二重チェックできます。
3. `X-Robots-Tag: noindex`・`robots.txt`・`Cache-Control: no-store` で、検索エンジンやキャッシュに載せません。プレビューURLは無効化しています。

テスト: `test/access.test.ts`

### T2: 学習者ごとにデータを分ける

学習者 1 人につき、SQLite 内蔵の Durable Object を 1 つ割り当てます（`src/lab/db.ts`）。キーは Access で認証されたメールのハッシュです（ローカルでは `lab_id` Cookie）。データは物理的に別の DB なので、脆弱版の SQL インジェクションで `DROP TABLE` を実行しても、読めるのも壊れるのも自分のデータだけです。共有の D1 のように「行の絞り込み条件をうまく外す」余地もありません。

テスト: `test/access.test.ts`（メールごとの分離）、各演習のテスト（別ブラウザから見えない）

### T3: 踏み台にさせない（ラボガード）

脆弱版のコードには手を入れず、`src/lab/guard.ts` が**レスポンスの外側から**安全網をかけます。

- **外部への持ち出し防止** … 脆弱版・修正版のページに `connect-src 'self'; img-src 'self' data:; form-action 'self'; base-uri 'self'; object-src 'none'` を付けます。XSS は成立します（`alert` もページの書き換えも体験できます）が、Cookie や入力値を**第三者のサーバーへ送る**ことはできません。
- **実在サイトへのリダイレクトを止める** … 転送先が予約ドメイン（`.example` `.test` `.invalid` `.localhost` `example.com` 等）以外なら、転送せずに「転送しようとした `Location`」を表示するページに差し替えます。`Set-Cookie` は維持します。
- **攻撃者ページは sandbox** … `/attacker/…` には `CSP: sandbox allow-forms allow-scripts`（`allow-same-origin` なし）を付け、ブラウザに別オリジン（`Origin: null`）として扱わせます。CSRF・クリックジャッキングのクロスサイト再現をこの 1 つの Worker だけで行うための仕組みで、攻撃の実行は必ず学習者のボタン操作です。
- `Referrer-Policy: same-origin` を付け、外部サイトへ Referer を渡しません（`no-referrer` だと同一オリジンの POST に `Origin: null` が付き、Origin 検証が誤動作します）。
- ラボ自身の状態変更（リセット・進捗）は、`Sec-Fetch-Site: same-origin` または `Origin` 一致のときだけ受け付けます。

テスト: `test/guard.test.ts`

### T4: 外部へ通信しない

アプリのコードは外部へリクエストを送りません。例外は Access の公開鍵（JWKS）の取得だけで、`src/lab/access.ts` に隔離しています。

`npm run check:egress`（`predeploy` で自動実行）が、`src/` の他のファイルに `fetch(` / `WebSocket` / `cloudflare:sockets` / `createRemoteJWKSet` などがないことを検査します。

> 通常の Workers には送信先を制限するファイアウォール機能がありません。つまりこの対策は**コードの規約と検査**であり、プラットフォームによる強制ではありません。演習を追加するときは `docs/AUTHORING.md` の安全ルールを守ってください。

### T5: 実環境に触れさせない

OS コマンド・ファイル読み取り・メール送信・HTTP ヘッダーの改行注入は、**純粋な JavaScript で作った擬似環境**で再現しています（仮想ファイルシステム、擬似シェル、生のヘッダー行の組み立てと解析）。Workers にはもともとファイルもシェルもなく、実際には何も実行・送信しません。

### T6: データを残さない

最後の操作から `LAB_TTL_HOURS`（既定 24 時間）たつと、Durable Object の alarm で全データを削除します。ホームのボタンでいつでも手動リセットできます。

## 残るリスク

- **学習者自身が被害者になる**: XSS・CSRF の演習は、あなたのブラウザで動きます。ダミーデータ以外（実在のパスワード、他サービスのログイン中のタブ）を使わないでください。脆弱版は専用のブラウザプロファイルで開くのが安全です。
- **Access を許可した人は誰でも触れる**: ポリシーに追加した人は、脆弱版を自由に攻撃できます。ただし他人のデータには届きません（T2）。
- **コードを GitHub に置く**: 脆弱なコードがそのまま公開されます。README の注意書きを残し、ここに書かれたコードを実運用に流用しないでください。
